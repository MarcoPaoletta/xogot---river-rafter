# Game Dev (Godot, MCP-first, product-ready)

You build Godot games that look and feel like finished Steam products, not like Godot tech demos. The default deliverable is **product-ready / steam-ready and polished, never slop.** When the user hands you a game proposal or says "make X game", assume they want a result a developer would look at and say "this is well made", not a working prototype.

**Central thesis (this drives everything):** the difference between product-ready and slop is NOT the mechanics, it is the **juice plus the post-processing**. Mechanics give you the minute to minute. Juice and a deliberate WorldEnvironment give the perception of a product. A game with simple mechanics but full feedback and a graded image reads as expensive; a game with solid mechanics and Godot defaults reads as a prototype.

There are two non-negotiable rules: **work through the Godot MCP (Rule 1)** and **treat polish as the product (Rule 2)**.

⛔ **And one sizing rule that comes before both: QUICK GAMEPLAY (Marco, 2026-10-25: *"I prefer 3 well polished levels over 30"*).** A Letta game is one signature mechanic plus at most two supporting ones, three to five short and visually distinct levels, and everything polished; the video shows about a minute and a half of gameplay, so content nobody films is polish that never happened. Read `references/quick-gameplay/quick-gameplay.md` before the GDD, the build order or the first level. Precedents: Overdue built 30 rooms and needed an Express route of 6 to 8; Splatwalk did very well on one heavily polished splat; Sushi Restaurant (five days) and Amber Run (five 30 to 40 s planets) were complete videos.

### Engine applicability: Godot, Unity, Unreal (Marco, 2026-10-20)

This skill is written for Godot, but a game on another engine uses it too (first case: Meadow Mechs for Aura, Unity 6.3 LTS with URP, built through Aura). `install_to_project.py` detects the engine and installs the same local, Git ignored copy; `skills/README.md` in the game says which engine it is.

**Engine independent, apply as written:** the central thesis (juice and post processing are the product), the quick gameplay scope (`references/quick-gameplay/`), the default bar (steam ready, never slop), the two acceptance gates (functional and perceptual), the concept match protocol (`references/concept-match/`), the visual feedback review, asset provenance and restoration (`references/asset-restore/`), the design principles of the polish references (juice, themed UI, tweened transitions, camera feel, screen fades, menu cuts), and everything under "Repo rules for every Letta game": the `setup-finished` tag, a commit plus annotated tag plus branch for every version (`vN`, full refspecs), builds only when Marco asks, one executable per version when he asks for it, and keeping this skill private and out of Git.

**Godot only, translate for another engine:** Rule 1 and its sub rules (Godot MCP first, one saved `.tscn` per game element, GDScript, `@tool`), `project.godot` and stretch `expand` settings, Godot node and API names in the references, and the APK and Godot AI recipes. The equivalent for Unity is to work through the editor tools of the project's bridge (Aura or a Unity MCP), one prefab per game element with named selectable objects, no hand written serialized `.unity`, `.prefab`, `.asset` or `.mat` files, statically typed C# with explicit public APIs, and tuning values in the Inspector or in project data. Instead of the `expand` rule, check the UI and the whole game at the design aspect ratio plus a wider and a taller one. For Unreal read `references/unreal-engine/unreal-engine.md` first: the Godot rules translated (toolsets of the editor MCP first, one Blueprint per game element, balance in a CurveTable, Post Process Volume with pinned exposure, Niagara), the measured MCP and editor traps, and the setup of the MCP in `references/engines-and-mcp-setup/`.

⛔ **Unreal playtests NEVER take the user's focus, mouse or keyboard (Marco, 2026-10-21, "super important").** Play In Editor runs inside the editor's own viewport and is driven through MCP and Python Remote Execution (`references/unreal-engine/tools/pie.py`: start, stop, `call` a Blueprint function instead of pressing a key, `tp`, `props`, clean frames with `HighResShot`, HUD frames with `shot showui`, slow motion for one shot effects). No floating Play window, no focus clicks, no system keys, no input bot unless Marco asks for it or agrees. Hold the editor lock while using the viewport; stop PIE before asset work, imports and level loads (the editor Python is blind during PIE).

If the project's own GDD or `AGENTS.md` contradicts a Godot only rule here, the project docs win.

### Final game: Expand and visual acceptance (Marco, 2026-10-13)

**Every final game runs with `display/window/stretch/aspect="expand"`, on desktop and mobile, in editor playtests and requested exports.** Configure it from day one. This supersedes the former desktop `keep` default and the APK-only exception. Expand preserves proportions while extending the visible area to fill the window; setting the flag alone does not pass acceptance.

- **UI:** large, legible text and controls; anchors and containers adapt to the actual viewport; menus, HUD, dialogs, pause and results stay visible and usable, without clipped text, overlaps, distorted art or controls outside the screen. Respect safe areas on mobile.
- **Whole game:** camera framing, characters, backgrounds, level edges, effects and fullscreen overlays cover the expanded view and remain coherent. No unintended black bars, uncovered background, exposed unfinished scenery or essential gameplay hidden behind the HUD.
- **Before declaring done:** inspect runtime screenshots at the design resolution, a smaller window, a wider aspect and a taller aspect supported by the target. Check both UI screens and active gameplay, plus resizing and fullscreen when supported. Save captures with dimensions and findings in `docs/evidence/` and `docs/BUILD_NOTES.md`; fix failures and inspect fresh captures before closing. If requested exports exist, verify them too. No binary export is implied by this gate.

Implementation and test matrix: `references/launch-settings/launch-settings.md`. Android device checks: `references/mobile-ui-touch/` §9.

## The default bar: steam-ready, never slop

A clip of 10 seconds should read as a finished game. Operative rule: **"If a feature works but doesn't feel good, it isn't done."** Concretely, none of these is acceptable:

- **Anything flat.** No tuned `WorldEnvironment` means it looks like a prototype. The Godot default render screams "demo". Getting it out of there is always the first visual job.
- **Anything that snaps.** No state change is instant or linear. Everything enters and leaves with a tween plus easing.
- **Any dead click.** Every important action (and invalid ones too) fires multi-channel feedback: visual plus light plus audio plus movement.
- **Default Godot UI.** No grey buttons, bars, or panels. Everything themed and animated.
- **An open loop.** Menu to game to game over / win, with clear screen states. Not a raw boot straight into gameplay.
- **Spaghetti code.** Static typing, docstrings per system, explicit public APIs, defensive access. Polish does not survive on top of mess.

### Two acceptance gates: functional and perceptual

A feature is not done when it works. It is done when it works AND reads. Split acceptance into two gates, and do not close a feature on the first one if it will be judged on camera:

1. **Functional gate:** states, collisions, economy, save, progression.
2. **Perceptual gate:** scale, hierarchy, legibility, feedback, rhythm, and zero placeholders.

A build can satisfy a self-consistent spec and still look like a prototype: a spec that defers UI, particles, fades and pickup celebration produces exactly that. If the user evaluates a screenshot or a clip, the visual criterion carries the same weight as the logic. When in doubt, screenshot: it catches what scripts and probes cannot (a dialogue box too tall, a coin halo that renders as a rectangle). This gate is why juice is measured, not assumed (see Rule 2).

## Rule 1: always work through a Godot MCP

### Rule 1c: every game element has its own saved scene (Marco, 2026-10-07)

**Scope: new builds adopting this revision.** Updating the canonical skill or its private mirror does not authorize updating skill copies, refactoring, or changing games already finished or being built. Leave those projects alone unless Marco explicitly requests a later update.

**Each game element is a reusable `.tscn` with named, selectable nodes and its own focused behavior script when needed.** This includes the player, enemies, projectiles, pickups, props, buildings, interactables, effects, HUD components and menu screens. A level composes instances of those scenes. Support nodes such as a sprite, collider, timer or marker belong inside their element's scene; they do not each need a separate scene file. Variants use inherited scenes or shared base scenes with data resources.

- **Author through the editor tools.** Create/save scenes, add/remove/reparent nodes, instance existing scenes, and change authored properties through the project's Godot MCP. Height, width, length, position, rotation, scale, anchors, offsets, collider dimensions and resource values are all editor property edits, including a change to just one number. Inspect the owning scene first, edit it or an intentional instance override, save, and reopen to confirm the value persisted. For Ziva or Xogot, use their own native scene/node/property tools as routed below, with the same modular result.
- **No scene generation in code.** Never hand-write serialized scene files, assemble an element with `Node.new()` and `add_child()` in `_ready()`, use a standalone generator or `@tool` builder to construct/bake its node tree, or generate the whole game from one script. Passing serialized scene text through an MCP file-writing tool does not make it editor authoring. Even a temporary particle burst, tracer or muzzle light starts from its own authored effect scene.
- **Runtime code drives behavior over authored scenes.** Spawners may instantiate saved `PackedScene` assets for enemies, projectiles, effects or generated level chunks, then move, animate, activate or free those instances. They may not build the instances' node trees or replace an authored level with a procedural constructor. Keep a preview of each spawnable element available by opening its source scene before Play.
- **Inspector edits remain authoritative.** Baseline geometry, layout and transforms live in the saved scene/resources. Expose tuning parameters in the Inspector and read the authored base values for movement, tweens and dynamic layout. Do not overwrite Marco's authored dimensions or transforms with fixed values in `_ready()`. Runtime animation or responsive layout is behavior; a requested permanent resize is an MCP authoring edit.
- **Modular code at every scale.** The main scene composes and its director coordinates. Each actor, UI component and system owns its behavior and communicates through signals or a small explicit API. A 3,000-line script containing the world, UI, actors and all node creation fails this rule even if the game runs. Prototype scope and small game size are not exceptions.
- **The main scene is `scenes/main.tscn`, and opening it in the editor shows the whole game world (Marco, 2026-10-20, Birdhouse Row).** Marco films the editor in the video, so the root scene is always named `main` (set `run/main_scene` to it, never `park`, `level`, `game` or the game's name) and its 3D or 2D viewport shows the actual world before Play: terrain, paths, landmarks, props, decor and every placed element, not an empty floor with markers. Author the world in the saved scenes through the MCP wherever you can. When the layout is generated from data (a world JSON, thousands of scattered decor instances) and baking it would bloat the scene, the world still has to be visible in the editor: give the world node an editor only preview. Mark the world script and the pure helper classes it calls `@tool`, build in `_ready()` only so the editor shows it, never set `owner` on the generated nodes, assign generated meshes only under `Engine.is_editor_hint()` and clear them on `NOTIFICATION_EDITOR_PRE_SAVE` (rebuild on `NOTIFICATION_EDITOR_POST_SAVE`), and duplicate any shared material you write shader parameters into, so saving never stores generated data in the `.tscn` or a `.tres`. Verify by reopening the scene with `force_reload` and taking an editor viewport screenshot that shows the world, then check that the saved `main.tscn` stayed small. This preview is the only allowed `@tool` world build and it never bakes anything; it does not relax the other no code generation rules. After editing a script from outside the editor, run `filesystem_manage` `reimport` on it first, or the editor keeps running the old script and the preview stays empty.

**Acceptance before calling the build done:** without pressing Play, open each element's source scene, select its named nodes, inspect its dimensions and move or resize it through the editor tools. Save and reopen to verify persistence, then run to confirm the authored change survives. Inspect the scripts for node-tree constructors and fixed startup overrides. A screenshot of a running game alone does not prove editor editability.

This is the priority for new builds when an older reference or example contains a node constructor or builder. Reuse its behavior and measurements, but author its structure as saved scenes through editor tools. Include the modular result in every new GDD, kickoff and agent doc, without updating existing game packages.

2. **No MCP addon at all → install Godot AI, at the latest 4.x** (Rule 1b). Exception: a project created as a Ziva starter (Skill 30, Tipo B, its docs say Ziva builds it) uses Ziva only. The current setup installs the official Ziva addon, unless Marco explicitly asks to leave it uninstalled. Read [Ziva starter setup](references/ziva-starter/ziva-starter.md) before preparing one. 3. **`addons/godot_ai/` exists and Ziva does not → Godot AI.** Update it to the latest 4.x if it is older (Rule 1b, step 6).

These games are built through a Godot MCP (Godot AI, or the project's own native editor tools when applicable) with the editor open. **All scene, node and authored property changes go through those editor tools.** Before doing Godot work:

- **Ensure an MCP is connected.** Check with `fennara_status` / `editor_state`. If Godot is not open or the plugin is not connected, ask the user to open the project and enable/connect the Godot MCP plugin before proceeding. Do not silently fall back to hand-editing project files.
- The only real exceptions to using the MCP are pure reading/searching, design discussion, and non-Godot files. **Any change to Godot state goes through the MCP.**

### Rule 1b: every new project ships with the Godot AI MCP, at the LATEST 4.x (Marco, 2026-09-18)

The Godot MCP we always use is **Godot AI by DLight** (`hi-godot/godot-ai`, addon folder `addons/godot_ai`). When you create or scaffold a Godot project for a video (a starter for a build, a course project to improve, anything an agent will build inside), installing it is part of creating the project, not a follow up. And it is always the **current 4.x release, never a version copied from an older project by habit** (3.x and 4.x do not interoperate, and the addon refuses to write an attach entry for a mismatched server).

Recipe, every time:

1. **Check the latest version, do not assume it.** `https://api.github.com/repos/hi-godot/godot-ai/releases/latest` (addon) and `https://pypi.org/pypi/godot-ai/json` (server). Both must agree; the per project pin uses that exact version. As of 2026-09-18 that is **4.1.0** (released 2026-09-11).
2. **Install the addon from the official release asset** `godot-ai-v4-plugin.zip` (the v4 addon; `godot-ai-plugin.zip` is the migration capsule, not the addon). Verify the zip's SHA256 against `godot-ai-v4-plugin.manifest.json` from the same release, unzip `addons/godot_ai` into the project, copy `LICENSE` to `godot-ai-LICENSE.txt` at the root (MIT, the repos are public).
3. **Enable it in `project.godot`:** `[editor_plugins] enabled=PackedStringArray("res://addons/godot_ai/plugin.cfg")` plus the autoload `_mcp_game_helper="*res://addons/godot_ai/runtime/game_helper.gd"`.
4. **Per project `.mcp.json` (gitignored) pinned to the same version**, attach transport by stdio wrapped in `pythonw` (`--from godot-ai==<version> godot-ai attach --port 8000 --ws-port 9500`). Copy it from the newest project that has one (Critter Camp, Barrow Knuckles) and only change the version if the release check says so. Never write a bare `uvx` and never a console python: a black window falls inside the recording. The full entry, why the `pythonw` wrapper is mandatory and where the addon writes the resolved command: `references/engines-and-mcp-setup/`.
5. **Verify without stealing focus:** `Godot --headless --path . --import --quit` must finish with zero errors (the plugin logs `MCP | plugin disabled in headless mode`, that is expected), then confirm the version in `addons/godot_ai/plugin.cfg`.
6. **Existing projects that are still on an older 4.x get updated the same way** before their build is recorded: replace `addons/godot_ai`, bump the pin in `.mcp.json`, re-import.

Why the version check is a step and not an assumption (Marco, 2026-09-18, setting up the launch day starters Barrow Knuckles and Coin Collector: *"put the Godot AI MCP we always use in all of them, but update it too. And update this in the skill: always install the Godot AI MCP that is up to date"*): the addon and the server are pinned per project, and copying a scaffold from an older project silently carries the old pin. Emberhold and Gravegarden were scaffolded on 3.2.4 a week before 4.x shipped, which would have meant a recorded build starting with a broken MCP.

The user scope entry in `~/.claude.json` (`godot-ai`, ports 8003/8004) is the fallback for ad hoc work; a project with its own `.mcp.json` overrides it inside that folder, and that is the one a recorded build uses. Ziva projects are the exception: Ziva is its own in-editor agent, so those starters ship without Godot AI. Marco's 13 October 2026 instruction replaces the old self-install step: install current Ziva during setup and verify it before opening. See [Ziva starter setup](references/ziva-starter/ziva-starter.md).

### Rule 1d: update EVERY brand MCP and plugin before the build starts, not only Godot AI (Marco, 2026-10-09)

Sponsor tools ship updates between the day a video is agreed and the day it is recorded, and a stale MCP or plugin makes the video wrong or unfair. SpriteCook, 2026-10-09: Kimo watched the SpriteCook against GPT image comparison and pointed out that the run did not use the model SpriteCook now offers (*"it should have used gpt image 2.5 here for instance"*) and that the plugin's UI looked the same as the ChatGPT version, so *"maybe you have to update the spritecook plugin"*. Marco's order (*"put in the skill that it always checks for MCP updates before starting (pixel engine, spritecook, whatever...)"*): this check is step zero of every build, for **every** tool the video touches (SpriteCook, Pixel Engine, Thrixel, AutoSprite, Fennara, Makko, Godot AI, whatever comes next), the same way Rule 1b does it for Godot AI.

1. **Update it.** A Claude Code plugin: `claude plugin marketplace update`, then `claude plugin update <name>@<marketplace>`, then reload plugins or restart the session. An MCP run through `npx -y <pkg>@latest` or `uvx`: restart the session so it pulls the newest release (pinned entries, like Godot AI in Rule 1b, get their pin bumped by hand). A hosted connector: disconnect and reconnect it so the client refetches its tool list. Codex or any other agent: update the package its MCP entry runs and restart the session.
2. **Check what the tool offers NOW, do not assume.** Call its own listings (SpriteCook `list_generation_models`, `get_preset_settings` and the `spritecook:*` plugin skills; Pixel Engine `check_balance` plus the model names `generate_sprite` and `animate_sprite` accept; the equivalent in any other tool) and compare them with the brand's last announcement or changelog. If the brand has a newer model, preset or feature than the tool lists, the tool is stale: update again or ask the brand's contact on Discord or email which version the video should use. For 2D sprite tools (SpriteCook, Pixel Engine, AutoSprite) the listings to read and what each model measured: `references/sprite-generation-2d/per-tool-notes.md`.
3. **Use the newest model or preset the brand offers**, never the old default, and put the tool, its version and the model names in the project's docs and in the Deal State (they are the evidence if the brand asks why a result looks the way it does).
4. **If the update cannot be done** (auth expired, marketplace unreachable, no newer build exists), say so BEFORE recording. Never start a recorded build silently on a tool that may be stale.

The golden cycle is always the same: **Inspect first, Edit second, Validate third, Screenshot fourth.**

**1. Inspect (look before you touch).** Never assume scene state, ask for it.
- `get_scene_tree` / `scene_get_hierarchy` to understand the tree and get real node paths (never guess paths).
- `get_node_properties` / `node_get_properties` for a full snapshot before changing a node.
- `project_settings` / `settings_get` for render, physics, input.
- `get_class_info` when you do not know the exact Godot API of a class (do not invent API names from memory).
- `search_shaders` / `semantic_search` to find what already exists.

**2. Edit (always through the MCP, never by hand).**
- Create and edit scenes and node trees through the MCP's editor authoring operations. Set authored properties through tools such as `node_set_property`, `material_manage`, `particle_manage`, the animation tools and `project_settings`. File-writing tools such as `write_or_update_file` are for script/shader source, never serialized scene text or scene generators. Use the connected tool's actual schema rather than assuming an operation name.
- **NEVER hand-write `.tscn` / `.tres` / `.res` as text.** They are serialized formats with UIDs and internal references, editing them as text corrupts them or desyncs them from the editor.
- **NEVER create nodes or build scaffolding from runtime code** (`add_child(Node.new())` in `_ready`). Structure (timers, markers, containers, collisions, sprites) is authored in each element's scene through the MCP. Scripts drive **behavior** over authored nodes. Runtime spawning instantiates saved scenes; effects and `@tool` builders are not exceptions to Rule 1c.

**3. Validate (verify nothing broke).**
- `script_diagnostics` after touching any script: zero compile errors before moving on.
- `validate_scene` to check the integrity of the edited scene.
- `get_runtime_errors` / `logs_read` for runtime errors.

**4. Screenshot (verify with your eyes, not in theory).**
- `screenshot_scene` / `editor_screenshot` to confirm it looks right. Post-process, glow, grade, juice: none of this is validated by reading code, it is validated by looking at the image. An environment change is done when the screenshot confirms it, not when the script compiles.

Never declare Godot work complete with "it should work". Inspect, edit through the right tool, validate diagnostics plus scene, and look at the screenshot.

### Who is building: you through an MCP, or Ziva

Rule 1 is what **you** do when you drive the editor yourself. It is not automatically what goes into a build package that a different agent will execute on camera. Before writing a spec, an `AGENTS.md` or a kickoff prompt, split the package in two and ask who the builder is. Only one half of it depends on the answer.

**The half that NEVER changes: what the delivered project has to be.** Same words for every builder, Ziva included. The game itself, loop, economy, model swap contract, art and audio bar, screenshot protocol, and above all this one:

> ⛔ **The whole world exists as named editable nodes inside the saved scenes before Play. Every game element has its own reusable source scene, with focused behavior, and levels compose instances of those scenes.** Terrain, plots, buildings, props, characters, routes, cameras, lighting and UI are all repositionable and resizable by Marco from the Inspector while recording. Spawnable elements have saved source scenes he can open before Play. Nothing required is assembled by a script at run time, because a world that only exists after Play cannot be touched on camera.

That is an **outcome**, not a method: it describes what the finished project looks like, never which tool built it. It goes into every package, verbatim, whoever builds. (Marco, 2026-09-08, when it got dropped along with the authoring rules: *"that rule about the whole world being visible, do include it"*, and *"for both, the rule is that I can move things in the scenes"*.)

**The half that DOES change: whether you explain the mechanics of editing.**

- **You, or another external agent, through a Godot MCP (godot-ai, Fennara): spell every authoring constraint out.** An MCP is a box of tools, not a method. Nothing in it stops an agent from writing a `.tscn` as text or scaffolding the scene in `_ready`, and it will do exactly that if the package stays silent. Rule 1 goes in almost verbatim.
- **Ziva: do not write authoring instructions at all.** Ziva is an agent that lives inside the editor and already owns the how: which tool creates a node, in what order to inspect and edit, when a file may be written by hand. Marco, 2026-09-08: *"you do not have to tell Ziva how to build scenes, do not give it restrictions, Ziva already knows."* Writing them anyway is noise inside a document that gets read on camera.

The test for any line in a package is exactly that. If it describes the **result**, it stays for both. If it describes the **mechanics of editing**, it only belongs in an MCP package.

### MCP gotchas from real builds

Each of these cost hours on a shipped project and none is obvious. Reach for them when an edit "did not take" or a system misbehaves:

- **Inspect ownership before editing a visible node.** A node you see on screen may belong to a shared nested scene, not the open one. Editing it from the wrong scene does not serialize. Open the OWNING scene (`npc_interaction.tscn`, not the NPC that instances it).
- **Resource cache: overwriting a `.tres` may not update the loaded instance.** When disk and memory disagree, save to a new path and reassign, or force reload, then retire the old asset.
- **Physics state is not a bool.** Flipping `enabled` on a hurtbox does NOT change `monitorable` or the shape. Wrap all three in one `set_enabled()` and use `set_deferred` inside signal callbacks. See `references/combat-vulnerability/`.
- **Radial gradient centering.** A `GradientTexture2D` with `fill_from = (0,0)` renders a rectangle in the corner: use `(0.5, 0.5)`. A `PointLight2D` texture must end in opaque black while the visual halo ends at alpha 0, or residual RGB lights up as a square.
- **Selecting an animation is not playing it.** A clip can boot selected and stopped; call `play()` when the name differs OR when `not is_playing()`.
- **Tests query semantic APIs and honor async state.** Expose getters (`get_core_count()`, `is_transitioning()`, `get_visual_alpha()`) instead of internal node paths, and once tweens make transitions non-instant, wait on an observable condition with a timeout, never a fixed frame count.
- **Retry and Restart preserve every mode's context.** Kelpfall's Journey needed both mode and chapter; forwarding only the mode passed every Endless test but silently left Journey on its pause or results screen. Exercise pause Restart, loss Retry, victory Replay and debug Reset in every mode through the real buttons. A mode's checkpoint, chapter and practice flag must survive the appropriate route. This check is portable across engines and browser games.
- **Sequential patches report transient errors.** Removing a constant before its uses, across several small patches, makes the editor report intermediate errors that are not the final state. Prefer an atomic patch when lines depend on each other, and run a full diagnostic only at the end.
- **One frame glitches only show in a frame contact sheet.** Capture every frame of an event (a hop, a transition, a respawn) into one image and read it. Property logs said "fine" on Reedway Ferry while the frame showed a giant sprite (physics interpolation, see Juice). It is also how hand-overs and transition timing are judged.
- **Synthetic input coordinates are WINDOW pixels, not design pixels.** With a 1920x1080 design viewport in a 1280x720 window, pushed events must be multiplied by 720/1080, or every tap lands off target.
- **A `game_eval` that "fails" with `EVAL_GAME_NOT_READY` may still have run.** Re-running it on Reedway started a second scene travel that collided with the first. Read the state before retrying.
- **The game running in the editor blocks every MCP scene write.** If Marco left a playtest open, stop it (the save is already on disk) and tell him it was stopped.
- **"It feels slow" gets measured, not guessed.** `Time.get_ticks_msec()` around the event before and after the fix, and the numbers go in the report.

## Rule 2: polish is the product

The condensed playbook. These are the patterns that separate a product from a prototype.

### Render and post-process (the #1 perception change)
The `WorldEnvironment` is roughly 80% of the look. Tune it BEFORE declaring any scene finished, and verify by screenshot.
- **Default stack:** Forward+ renderer (never Mobile/Compatibility), Jolt Physics, D3D12 on Windows, **TAA** on (MSAA 2 as complement), GDScript.
- **Filmic tonemap, not linear.** `tonemap_mode = 2` (Filmic) or `3` (ACES). This alone separates "real game" from "flat".
- **Ambient light tinted by mood,** not default white. Cold blue, low energy for horror/sci-fi.
- **Selective glow/bloom.** High `glow_hdr_threshold` (~0.95) so only truly bright things (lights, emissives, muzzle flash) bleed light. High threshold means selective glow, not washed out.
- **SSAO** (radius ~1.1) so corners and contacts darken, giving volume. SSIL outdoors when realistic.
- **Fog for depth.** Classic fog plus **volumetric fog** sells atmosphere and turns light beams into visible volumes (god rays). Set `light_volumetric_fog_energy` on lights.
- **Deliberate color grading:** nudge contrast up, pull saturation down for a designed look. These are designed values, not defaults.
- **Performance:** on dense levels, do not blindly enable SDFGI/SSIL. Tune the environment to mood and budget.
- Real PBR materials (metallic/roughness/emission), never flat colors.
- **Screen shaders for mood:** one full-screen `canvas_item` overlay = vignette + permanent animated film grain + tints driven by uniforms from GDScript, all in one draw call. Plus a damage vignette tweened by code (rises fast ~0.06s, falls slow ~0.45s). In 2D (no WorldEnvironment): a dark semi-transparent `ColorRect` on a background `CanvasLayer`, `PointLight2D` for glowing objects, and short reusable canvas shaders.
- ⛔ **2D water and its wake are ONE surface, never two layers** (Marco, 2026-09-24, Reedway Ferry). A world space water shader draws the cells; the boat only paints a foam MASK into a `SubViewport` that mirrors the camera, and the water turns that mask into foam with its own cells and parts the cell network around it. Foam fades from white to fully transparent with age, stern trail only, no bow "arrow" arms. Recipe, the blending trap and the scripts: `references/water-foam-2d/`.

### Zero z-fighting: prevent it and verify in motion (Marco, 2026-10-13)

**Z-fighting is a blocking visual bug, including in builds still in progress.** Do not wait for Marco to circle it. Floors, region tiles, borders, overlays, water and world-space labels must not compete at the same depth. WorldOS / Modern Day Strategy is the reported example; Marco had already alerted its build session. This canonical update does not authorize changes to that game or refreshing its skill copy.

- **Prevent duplicate and coplanar faces:** one visible base surface per area; adjacent tiles meet without overlapping top faces. Inspect imported bases under props. Intentional overlays use separation along the surface normal, measured at the real scale, or decals supported by the target renderer. Author named offsets in the owning scene/resource through editor tools, per Rule 1c.
- **Inspect before patching:** isolate suspect surfaces temporarily, inspect world transforms and restore visibility. Motion and isolation distinguish depth competition from clipping, transparency sorting or aliasing. Render priority, disabled depth testing, antialiasing and blur are not general fixes for opaque coplanar geometry.
- **Camera precision:** after correcting geometry, increase `Camera3D.near` only as far as close gameplay permits and reduce unnecessary `far` distance. Verify neither clips required geometry. No universal offset or clip-plane value replaces testing the actual scale and renderer.
- **Acceptance requires movement:** inspect every region/repeated instance at all supported zooms/angles, during camera transitions and states adding overlays. Require zero flicker, alternating patches or broken labels/borders. Save a runtime clip or consecutive frames in `docs/evidence/`, and affected nodes, final values and results in `docs/BUILD_NOTES.md`. Save/reopen and repeat. A still frame or green diagnostics alone cannot pass.

Procedure, original example and primary sources: [z-fighting prevention and QA](references/z-fighting/z-fighting.md).

### Concept match: when a concept image exists, it IS the acceptance test
Every Letta collab build starts from a concept image the client approved, and that image is what the video's side by side and the thumbnail will show. So the concept is not a mood board: **camera angle, framing, lighting and `WorldEnvironment` are matched to it by a measured loop, never by feel** (Marco, 2026-09-13: *"key is comparing with photos, concept vs gameplay, I want something very similar in camera angles, lighting and world environment"*).
- **Name the camera:** `ConceptCam` (or a `ConceptPose` marker the gameplay camera adopts at the start, in runners and side scrollers), perspective, kept in the saved scene, with a dev only snap action (Tab) removed from the final build.
- **Author the concept region by hand** (the first chunk of an endless game, the whole scene otherwise): same props, same silhouettes, same relative positions.
- **Shoot after every visual milestone** at the design resolution from the concept pose, compose concept left / screenshot right, save as `docs/evidence/comparison-NN.png`, numbered, never overwritten. Check in order: horizon and camera height, distance and FOV, subject position, main silhouettes, props, background landmarks, sky, water or ground colour, sun direction and shadow softness, fog, glow, grade, UI. Fix the biggest mismatch, re shoot, repeat, five to ten rounds.
- **Light is matched by value:** the GDD carries target colours and sun angles read from the concept, `docs/BUILD_NOTES.md` carries the final values.
- **The one to one rule (Marco, 2026-09-20, Reedway Ferry):** *"the water, the lighting and some sections of the game or scenes should be one to one identical to the concept images. For example, the layout of the city, all of that has to be the same."* The camera and light loop is not enough: where a concept shows a layout (the town, the sea, the harbour, the HUD), the build COPIES it element by element and with the same count (if the sprite sheet has fewer sprites than the concept has buildings, sprites are reused, positions are never dropped), and the light of each concept (lanterns, warm windows, sun, shadows) is reproduced in Godot and judged in the comparisons. It opens Section 1 of the GDD (precedent: `Reedway Ferry - Build GDD.md` §1, "The one to one rule") and goes into the repo's `KICKOFF` / `AGENTS`. A GDD line like "the check is the layout language, not the count" contradicts this rule: fix it.
- ⛔ **A new world, zone or episode of an existing game reuses the approved screen architecture** (Marco, 2026-09-29, Reedway Ferry Ep 2: *"the town format has to be like Lilyport; we can change the floor type, even have the buildings off the water, but the view has to be the same"*). Same view, same camera scale, same character height, same way the scene is built (lots, chained ground segments, one sprite per building). Only the material changes (floor, lot ground, palette, landmarks). ⛔ **A walkable floor is never one big painted image**: it is a piece that chains or repeats (like `lilyport_ground`), with every building a separate sprite on its lot. If a GDD, a brief or a concept asks for a different view or a single painted base for a screen type the game already has, stop and flag it to Marco before building it; do not build it as specified.
- **`comparison-final.png` is item 1 of the definition of done.** Without it the build is not done. The kickoff prompt Marco pastes into the build session names the protocol and `comparison-final.png` as item 1 of done. How to (MCP screenshots, the compose script): `references/concept-match/`. The drop in GDD block: Skill 5 `1 - Build GDD/patterns/concept-match.md`.

### Cameras: always perspective, never orthographic (Marco, 2026-09-10)
**Approved project exception:** Carved Colossus (Marco, 2026-10-12) explicitly uses an orthographic side camera with zero pitch, yaw and roll. Preserve that approved framing. This exception does not change the default for other projects.
**No camera in Marco's games is orthographic.** When he says "view like the preview" or "isometric" he means the **angle** (a high camera at 45 degrees of yaw), not the projection: *"Always perspective for the camera... that for sure. Isometric is very flat"* (UNDERCROFT). An orthographic camera flattens depth and strips the render of the finished game look he wants on camera; and with both cameras in perspective, a camera switch is a single tween of position, rotation and FOV, with no projection change.
- Every top down or "isometric" view is specified as a `Camera3D` in perspective with a low FOV (30 to 35), pitch ~50 degrees, yaw 45, at a fixed distance from the player, rigid follow on the ground plane only (X and Z, never height or angle). Never `PROJECTION_ORTHOGONAL`.
- If the game also has a third person camera, it swaps with a button and a ~0.45 s tween; the GDD says so explicitly.
- Goes with the rest of his mobile bar: the touch UI exists but **is not visible on desktop** except through an exported checkbox (`force_show_touch_controls`), and "mobile-ready" does not mean exporting an APK unless he asks (see "Builds (APK / EXE)" under Repo rules). **Exception (Marco, 2026-09-24, Reedway Ferry):** when the joystick is the game's only control (no keyboard steering by his call), it is visible on PC too, fixed at the bottom centre. Details in `references/mobile-ui-touch/` §10a.

**2D top down cameras on a vehicle (Marco, 2026-09-24, Reedway Ferry).** The 3D rules above do not cover a 2D `Camera2D`, so these do:
- ⛔ **North up by default.** A camera that turned with the boat made him dizzy (*"me marea"*). The turning camera stays only as a Settings option. When a default flips, **rename the setting key** so old saves pick up the new default.
- ⛔ **Characters on the vehicle rotate with it** (hull and crew turn together); counter rotating the crew to stay upright looked wrong to him. World UI (speech bubbles, hearts, damage numbers) and characters on the ground stay upright.
- ⚠️ **Detaching a camera that is the child of a rotating node** (`top_level = true`) must keep its real on screen rotation and then ease to the target, or the view snaps sideways.
- **Zoom levels are Marco's, tuned on screenshots, and move in steps.** Sea camera 1.25, then 0.625 ("too far"), then 0.8125 (+30%). The travel dive into a town: 2.6x was "way too much", 1.3x stayed. State the number you picked so the next round can tune it.

### 3D character animation: blend, never snap (Marco, 2026-09-08)
**Between ALL animation states there is a blend, never a hard cut**, default **~0.75 seconds** (Hardhat Hollow: *"key that between all the states there is a good animation transition, like with a blend time of 0.75 say, so the transition is not harsh"*). What bothers him is the hardness on camera, the same criterion that made him drop Tripo's stiff `idle`: a snap between clips looks exactly as cheap as a stiff idle, and his bar is product-ready.
- Build the transitions in an `AnimationTree` with a BlendTree and leave **every blend time as an exported inspector property**, never a constant in code (the same criterion that already rules Banana Brawl). 0.75 is the default for idle, locomotion, work and celebration clips.
- ⚠️ **The exception is clips whose contact frame fires gameplay or audio** (a hammer blow, a pickup, a hit): there a 0.75 blend in eats the frame and the sound lands late, so they blend in at 0.20 to 0.30 and out at 0.75. And the state change commits on the input, never when the blend ends.
- ⛔ **Tripo characters: the base idle is `look_around`, never Tripo's `idle` clip** (it comes out stiff on camera). Full rule and the catalogue caveats in Skill 6.3 `3 - 3D Models/style-guide.md` Part F.5b.

### Juice and game feel
Hard rule: **nothing snaps, nothing is linear, nothing is a dead click.** When in doubt, add a tween, a flash, a pop, an ease. And stack **multi-channel feedback**: one layer feels cheap, three or four simultaneous layers feel pro.
- **Motion:** spawn pop (scale 0 to 1.2 overshoot, `TRANS_BACK`), tweens with easing everywhere, fade-out instead of direct `queue_free()`, framerate-independent smoothing (`1 - exp(-k*delta)`, never fps-dependent lerp).
- **Impact feedback in layers:** emissive hit-flash (~0.07s) + one-shot particle burst + damage vignette (shader) + screen shake with decay + brief hit-stop (~0.35s delay before pausing the tree so the moment reads).
- **Audio-visual sync by signal, never by parallel timers.** The system that plays the sound emits a signal and the visual reacts (a heartbeat thump emits, the red shader pulses). Footstep fires at the low point of the headbob, not on a loose timer.
- **One single intensity curve (0..1) drives the whole mood.** Tie post-process, color, audio volume, heartbeat/music pace, and UI to the same value, with non-linear curves (`pow(x, 1.7)`, thresholds) so it starts late and accelerates. Propagating ONE intensity through the whole stack is what separates polished from loose effects.
- **Rejected feedback:** invalid actions (full health, empty reload, not enough coins) still fire a reject pop / shake / red flash. Never a dead click. Make the cause of damage legible (freeze the world, highlight only the offender).
- ⛔ **Sprite hand-overs are invisible** (Marco, 2026-09-24, Reedway Ferry: "1:1 with the seated sprite"). When a character moves between two representations (standing on a dock, seated on a boat), it flies along an arc re-aimed every frame to the exact target, lerps rotation and on screen height into the target pose, cross fades with a pixel identical copy of the target sprite over the second half, and only then swaps. One copy per direction, drawn above the vehicle during the hop, confetti where it lands. Recipe and scripts: `references/character-anchors-handover/`.
- ⚠️ **One frame giant sprites = physics interpolation.** With `physics_interpolation = true`, a 2D or 3D node that is rescaled, teleported or shown again draws one frame interpolated from its old transform. Call `reset_physics_interpolation()` AFTER making it visible and setting the new transform. Only a frame capture shows it (MCP gotchas).
- ⛔ **Tycoons (gather, carry, process, sell, spend, unlock) follow `references/tycoon-juice/`** (Marco, 2026-10-17). Every transfer of value is a visible object on an arc with squash, ripple, pitched sound and a number; the player carries goods in a trailing back stack; stations chop with a tick per beat; money is physical and the counter only rises as coins land; progression is standing on unlock pads, never a menu. Read it before writing a single tycoon system.
- **Slow motion** with a custom `world_time_scale` that only enemies/spawner consume, not global `Engine.time_scale`, so the player stays responsive.
- **Measure juice in results, not in nodes.** The existence of a `camera_trauma_requested` call is not shake: trauma 0.18 with a quadratic curve and `shake_max_offset` 10 peaks under 1 px and vanishes in compressed video. A DashBar that exists but never shows the recharge curve communicates nothing. A glow with a miscentered gradient adds noise, not focus. At the perceptual gate, verify the actual pixels, amplitude, alpha, particle count and movement distance, plus the state before and after, and set a perceptual minimum for shake so it survives video compression.

### Video-ready games: the build is filmed (Marco, 2026-09-24)
Every Letta game ends up on camera, so two things are part of the product, not extras. The GDD must specify both.
- ⛔ **F1 opens a simple debug panel for showing progression on camera.** Big, readable buttons, themed like the rest of the UI: add currency (+100, +1000), skip or spawn the next wave or level, unlock the next area, god mode for whatever the player protects, time scale 1x/2x/4x, and a reset of the game's signature state (clear paint, respawn, etc.). Its job is to let Marco jump through the progression in seconds while recording, so every step must show its normal feedback (coins tween in, the unlock plays its reveal), never a silent state jump. Hidden by default, F1 toggles it, it never ships visible. It exists in **every playtest build** too, not only for the recording, and two buttons are always there (Marco, 2026-09-24, Reedway Ferry): a spammable "+100 coins" and **"Erase save, start over"**. Quick and plain beats elaborate; one flag turns it off for release.
- ⛔ **The WOW is in the first minute, nothing is held back.** From the first wave or level every enemy type (and every signature mechanic) already appears, the screen is busy (many enemies at once), and the player starts with enough currency to build or use a lot right away. Difficulty ramps by count, speed and pressure, never by slowly revealing content. A slow tutorial ramp that saves the spectacle for minute ten kills the video: the viewer sees the first minute.
- ⛔ **Small and polished beats big and rough (Marco, 2026-10-25).** Three to five short, visually distinct levels, one signature mechanic polished until it looks great on video, level N+1 only after 1 to N pass the perceptual gate, and when time runs short the cut is content, never polish. A game that is already big gets an Express route (6 to 8 of its best levels, everything unlocked on the way, finale at the end), never a silent deletion. Full budget, evidence and GDD block: `references/quick-gameplay/quick-gameplay.md`.

### UI and game loop
- ⛔ **THE FONT IS DOWNLOADED FROM THE INTERNET, ALWAYS. Godot's default must not survive anywhere in a shipped game** (Marco, 2026-08-01, said twice: *"have it look for fonts on the internet or something like that, there cannot be UIs left with Godot's default or empty font"*). A menu in Godot's default face reads as a prototype in the **first second of the video**, which is the exact opposite of what these videos argue. So: go to Google Fonts or Font Squirrel, pick a face that fits the game's world, **try a few in the real menu** before committing, verify the licence allows commercial embedded use (SIL OFL and Apache 2.0 are fine, "personal use only" is not), **commit the file into `assets/fonts/` with its licence beside it** (never depend on a font installed on the machine), and set it as `gui/theme/custom_font` so every Control inherits it. **One family per game.** Two failure states, both broken: a control in the engine default, and a control with **no font resource at all**, which falls back to the same default silently. That includes the pause menu, every prompt, and **every debug or placeholder label left in**. Verify by walking the scenes, not by assuming the project theme covered it.
- **Always themed:** `StyleBoxFlat` (rounded borders, margins, own colors), custom fonts, buttons that tween scale on hover (1.06) / press (0.97). Default Godot UI is the clearest mark of slop.
- ⛔ **2D games with generated art: the UI is ONE generated panel pack, used at native shapes.** One image with every panel (small and medium square, large, tall, wide bar, medium bar; no tiny bars or thin strips), thin border, same family as the HUD. Each slot takes the piece whose native shape fits and scales it uniformly; nine patch only when a slot truly needs another aspect, with margins that cover the outer corner radius. Generous inner padding, one centered item per slot, square cornered progress bars. Marco's corrections on Reedway Ferry, full recipe in `references/ui-art-pack/`.
- **Always fade,** never hard show. HUD communicates state by color (blue bar to red under 35%) plus tweening. ⛔ **A cross fade means both sides fade AT THE SAME TIME**, never one after the other; wrap each composite (a character over its island) in a `CanvasGroup` so its parts do not go see through over each other mid fade (Marco, Reedway Ferry title showcase).
- ⛔ **Minimal HUD: if the world already shows it, the HUD does not repeat it** (Reedway: the seats panel went away because the passengers are visible on the boat). World attached UI (price tags, bubbles) never covers its object.
- ⛔ **Every unlock visibly does something** (Marco, 2026-09-24): in a builder, each building gives a stat bonus shown in a popup when it completes. And when Marco gives an order (he drew the unlock order with numbers on a screenshot), use it literally.
- **Bigger reads better, and collision scales with the art** (Reedway's boat went to 1.5x). **Expect the first build's speed to be too high:** Reedway's top speed was cut 40% after the first playable. Joystick, ring interaction, title screen, town builder and coin juice rules from the same game: `references/mobile-ui-touch/` §10.
- **Complete screen states:** skippable intro, reactive HUD, blocking modals, game over, win. Each handles its own fade. Stacked in `CanvasLayer` by depth (FX < UI < Screen).
- **Pause-safe:** anything that must keep animating while `paused` uses `process_mode = ALWAYS` and/or `TWEEN_PAUSE_PROCESS`.
- **Closed loop:** menu to game to end screen, explicit FSM, clean restart.
- **Audit placeholders before closing a scene.** Hunt world-space `ColorRect` with no visual intent, floating Labels that describe gates ("7 CORES REQUIRED"), spawn/checkpoint marker sprites, empty portrait slots, debug text in the HUD, default-style bars, and off-palette colors. Not every rectangle is a placeholder: an intentional panel has style, margins, hierarchy and function. And a Theme is not enough, colors leak through `theme_override_colors`, `modulate`, `self_modulate` and scripts, so audit those too. Full recipe in `references/ui-polish-2d/`.

### Asset pipeline

- **From the first asset import, maintain a versioned `docs/ASSET_RESTORE.md` or an existing registry with equivalent restoration fields** (Marco, 2026-10-27). Read `references/asset-restore/asset-restore.md` and use its metadata template. Update it with every import, replacement and postprocess change, and before version handoff or cleanup. Record exact project-relative paths, original names, provider/pack/version/license when known, restoration steps and dependencies/scripts. **Marco confirmed on 2026-10-27 that his generated assets remain in his own provider accounts:** provider plus original names/paths and manual account retrieval steps are sufficient, including Tripo, Meshy, Hyper3D, SpriteCook, Pixel Engine and his other generation services. Record `asset/task IDs not recorded` when absent; missing IDs or direct URLs do not block cleanup or trigger repeated questions/research. Keep known stable public-pack URLs and versions, but never credentials or signed URLs. Flag only genuine gaps outside the accepted account confirmation, such as unknown providers or irreplaceable authored data; do not claim an API download test. This project metadata may be pushed; the private skill and its local copy remain ignored. This applies to new and future builds and explicitly requested metadata for old projects, without updating their skill copies or game source.
- ⛔ **2D sprites generated through an MCP (SpriteCook, Pixel Engine, AutoSprite or any other) follow `references/sprite-generation-2d/`** (Overdue, 2026-10-23, the best SpriteCook art so far). One pixel density for the whole game (k = 1 in every file, one display scale), probed per model before any wave; generated pixel art is never scaled up or down (Kimo, SpriteCook); anchors first; a short style lock plus a strict flat side or front view lock in every prompt, and a budgeted view audit (Overdue: 71 of 125 stills came back three quarter, 2,336 credits to fix against 300 to 500 planned); every result looked at; raws plus a json record per job, a manifest and a credit ledger with a ceiling; clips from the approved still, checked frame by frame; big assets composed or rigged from same density pieces. Makko has no MCP: Skill 27 plus `references/sprite-animation-import/`.
- **Sponsor-tool models** (typical for these videos): `.glb` with embedded PBR, organized by type, import with `generate_lods` / `create_shadow_meshes` / `ensure_tangents`, material overrides baked into the `.tscn` as editable-instance diffs.
- ⛔ **A sponsor asset goes into Godot AS DOWNLOADED** (Marco, 2026-09-20, after finding `process/size_limit=2048` on the 44 `.jpg.import` of Steam and Snow: *"I never told you to limit the textures or anything... everything has to be exactly as it came out of Tripo, it has to be 8K, because otherwise it is going to look like shit. The way the model downloads is how it goes into Godot. Any problem or whatever, tell me, but it goes as it comes."*). No texture cap, no rescale, no decimation, no LOD or `root_scale` tweak on your own initiative: the headless import generates the `.import` files with their defaults and none is touched. The texture quality is part of what the video shows of the tool, and any reduction of the asset is Marco's decision. If a playtest surfaces a real problem (VRAM, load time, frame rate), measure the numbers and present them to him with the option; he decides. Same family as the gltfpack rule (Skill 6.3 `style-guide.md` A.7c: simplify only if Marco asks) and the no unrequested code rule. Written in Skill 6.3 `tripo-download-to-godot.md` §5.
- **One folder per 3D model** (`models/<category>/<model>/<model>.glb` plus its textures), the GLB renamed on download, `.import` files deleted when files are moved from outside the editor. Rule of Marco, 2026-07-19, detail in Skill 6.3 `style-guide.md` A.7b.
- ⛔ **An asset pack is a BANK, not a checklist** (Marco, 2026-08-18, leaving the three Chatforce games sourced). Most models of a pack are never used, and a whole pack left unused is a normal outcome, not a gap. Downloading a pack creates no obligation to place it; the real risk is the inverse: an agent that treats the folder as an inventory to exhaust inflates the game's scope to justify models it downloaded, and mixes packs from different authors until the game looks like a collage. Fewer packs read better. The `ASSET_MANIFEST` (or the equivalent doc) rules over what the game needs and the folder answers to it, never the reverse. Whatever sits in `vendor/` and is not pointed at by a manifest row is **spare stock** and gets no note. Pick the model that fits the plan, the scale and the palette; never place one because it exists. When several packs are candidates, the style test can **discard whole packs**, and the discarded one stays on disk without being copied into the project. Write the rule in the docs the agent reads (`AGENTS.md`, `ASSET_MANIFEST.md`, `KICKOFF_PROMPT.md`), not only in the chat.
- **Choosing between packs or models: Marco decides from photos rendered INSIDE the real scene, with the real light** (2026-09-10, picking enemies for UNDERCROFT: a lineup on a grey plane with two suns was discarded on sight, *"those photos are shit... put them in with real light and in the preview scene or something like that, because like this it is hard to decide"*). The criterion is how the assets will live together in the game (palette, scale against the player, whether they fit the world), and that only shows in context; an isolated render gives him nothing and is wasted time. Recipe: Blender headless on the environment pack's preview `.blend` (for the ruins pack, the room of `Preview.blend` with its 12 lights), import the candidates via glTF, force the `Idle` clip on each armature (the importer hooks the first clip alphabetically, `Crawl` for example, and they come out lying down), put them on free tiles next to the player at real scale, camera at the game's angle. Two shots per set, wide and close, EEVEE is enough. Next to the photos, the **measured** table of clips per model (read `animations[].name` from the gltf), because the final call came from there: the Zombie Apocalypse Kit zombies won for having `Run_Attack` and `Crawl`, not for the photo. Pipeline in the UNDERCROFT session scratchpad: `monsters/render_scene.py`.
- **To place something by its on-screen silhouette, measure the render, not the mesh.** Critter Forge 2026-09-23: framing battle creatures a fixed pixel margin from the screen edge using the CPU skinned vertex box (skin every vertex through `Skin.get_bind_pose()` and `get_bone_global_pose()`) missed a fox's ears by 75 px, and Python skinning of the same GLB agreed with the wrong box, so the gap is between the mesh data and what the GPU draws. What works for any model: put the object's `GeometryInstance3D`s on a spare visual layer, render one frame into a throwaway half size `SubViewport` (`transparent_bg`, a camera copying the real camera's transform, fov, near, far and `keep_aspect`, `cull_mask` set to that layer only, and a camera `Environment` with `BG_CLEAR_COLOR` so the world sky does not fill the background), await two `frame_post_draw`, read `get_texture().get_image().get_used_rect()`, restore the layers, free the viewport. Two frames, exact pixels, no per model tuning, survives a model swap. Verify with a with/without pixel diff of real captures.

- **A Node3D hidden while its ancestor moved renders at a stale transform when shown again.** Critter Forge 2026-09-22: the player's creature wrappers are siblings under one `CharacterBody3D`, switched with `visible`. The body teleported to the battle mark while the fox was hidden; when a forced switch showed it, it drew nowhere, although `visible`, `is_visible_in_tree()`, `is_position_in_frustum()` and every global transform in the chain were correct, and a freshly instanced copy at the same spot drew fine. Not occlusion, not layers, not the AABB, not physics interpolation (switching it off on the subtree changed nothing). The fix is any set on the shown node's own transform: `shown.transform = shown.transform` plus `force_update_transform()` right after `visible = true`. General rule: when you toggle a 3D subtree with `visible` and something moved its parent meanwhile, re-set the transform on show. And when a node "is there but does not draw", run the ladder in this order, each as a one line experiment in a throwaway harness: in frustum, visible in tree, layers versus cull mask, fresh clone at the same spot, nudge the parent, nudge the node itself. The clone and the nudge are the two that separate "state" from "render".

- **Godot MCP: a reparented node loses its owner and silently never reaches the `.tscn`.** Hit on Critter Forge 2026-09-22: four battle buttons were moved to a new parent through the MCP, rendered correctly in every play run for an hour because the editor keeps them in memory, and were simply absent the moment the scene reloaded from disk, taking a committed scene with them. Godot only serializes nodes whose `owner` is the scene root, and reparenting does not reassign it. So **prefer create plus configure plus delete over reparent**, and after any structural edit verify on disk, not in the editor: `grep 'parent="Your/Path"' scene.tscn` must list what you expect before you trust a capture or a commit.

- **Where to find assets when Marco asks "find me assets for game X":** the curated catalogue is `Letta/Knowledge/Game Development/asset-sources.md`. The two go to sources ("they are god", Marco's words) are **Kenney** (kenney.nl, ~40k CC0 assets, 2D/3D/UI/audio) and **Quaternius** (quaternius.com, low poly 3D CC0, environments and rigged characters); third 3D staple **KayKit / Kay Lousberg** (CC0). Marco's priority: **100% free and WITHOUT attribution** (CC0 or equivalent) for Letta videos. Since 2026-09-17 (*"they should not be the usual ones... that we already use"*) the catalogue has a section of CC0 packs verified page by page beyond Kenney and Quaternius (KayKit complete, Elbolilloduro PSX, Loafbrr, Fertile Soil, Tiny Treats, valsekamerplant PSX city, Gobkit, plus a rejected by licence list): use that section first when he asks for a new base. Inside one site licences differ (itch.io, OpenGameArt, Sketchfab): confirm the specific pack, not the site. Sketchfab and Quixel/Fab are not clean free sources. One coherent style beats mixing, and the asset never replaces the polish.
- **Modular 3D levels:** `MeshLibrary` + `GridMap`, with the navmesh baked at runtime (`bake_navigation_mesh()` in `_ready()`).
- **When no assets exist:** author placeholder primitives, their materials and dimensions in each element's scene through the MCP. Procedural variation may drive existing resources or arrange instances of saved scenes, never construct the element's node tree. Synthesized SFX may be baked offline as described below.
- **Synthesized audio gets baked to a compressed file, never generated at runtime (Marco, 2026-09-22).** The generator is a `tools/make_audio.py` that runs once offline and writes real assets; the game only loads them. Long beds (music, ambience) ship as **OGG Vorbis**, not WAV and not MP3: on Critter Forge the two 45 second loops went from 3.97 MB each as 22 kHz stereo WAV to 0.14 and 0.23 MB, the whole `assets/audio/` from 8.5 MB to 1.1. MP3 is the wrong pick for anything that loops because the encoder padding puts a click at the seam; Vorbis loops sample exact. **Short Foley stays WAV** so a one shot never waits on a decoder, and it costs nothing anyway (18 clips, 0.6 MB). Bake with `ffmpeg -c:a libvorbis -q:a 5` and delete the intermediate WAV plus its `.import` in the same script, so the repo never carries both. In code, loop an `AudioStreamOggVorbis` with `loop = true` and `loop_offset = 0.0` (the `AudioStreamWAV.loop_mode` dance does not apply), and duplicate the stream before setting it so two players never share one resource.
- **A seamless synthesized loop is a frequency problem, not a crossfade problem.** Quantize every partial to a whole number of cycles over the loop (`round(f * duration) / duration`) and run every envelope on a wrapped clock (`u = (t - start) % duration`), and the tail of the last event becomes the lead in of the first with no fade needed. Measured seam on Critter Forge's 45 s bed: 0.0005 of full scale. Verify it, do not assume it: read the WAV back, compare the last sample against the first, and check the spectral centroid (a warm pad lands near 270 Hz, chiptune lands at 1.5 to 3 kHz), which is also how you prove to a client that the track is not 8 bit.
- **Greybox first:** build with placeholder primitives, finish the systems, swap final art at the end.
- **Audio is a product decision, read the constraint first.** The default is to ship audio, because mute is the most common gap: one-shot pools pre-instanced (zero runtime `new()`, zero hitches), loops set in code, reactive audio where it applies. But juice does not mean audio is mandatory. If the user asks for zero audio, honor it and strip the whole architecture too (autoloads, volume settings, options UI), not just the runtime playback, keeping editor authoring tooling. Four modes: full audio / placeholder audio allowed / runtime silent with reserved architecture / zero audio footprint. Starling shipped zero audio footprint on explicit request.
- ⛔ **Every game boots MUTED, and `M` unmutes (Marco, 2026-10-05: *"mute everything by default, unmute with M"*).** The audio is still fully built (assets, pooled one shots, loops, reactive audio), so "never ship mute" below means never ship a game WITHOUT audio, not a game that starts audible. ⛔ **WHEN: this is the FIRST thing installed in the project (workflow step 2b), before any sound exists, not a finishing touch (Marco, 2026-10-05: if it lands at the end, the PC makes 300 noises during the whole build).** Every run the agent does while building must already be silent. Implementation: an `Audio` autoload (or the existing audio manager) sets `AudioServer.set_bus_mute(AudioServer.get_bus_index("Master"), true)` in `_ready()`, and an `InputMap` action `toggle_mute` bound to `physical_keycode` `KEY_M` flips it. Mute the **Master bus**, not individual players, so every present and future sound is covered and nothing slips through. Keep playing the streams while muted (do not stop them), so unmuting lands mid loop with the reactive audio already in sync. The mute toggle stays alive when the tree is paused (`process_mode = PROCESS_MODE_ALWAYS`) and on every screen (intro, HUD, pause, game over). Show a small, readable speaker icon plus the label `M` in a screen corner (muted / unmuted states, tweened, themed, big enough to read), so the player and the viewer see why it is silent and how to turn it on. Persist nothing: every launch starts muted. Verify: a script or screenshot run confirms the Master bus is muted at boot and that the `toggle_mute` action flips it. The zero audio footprint mode skips all of this.
- **Product details:** boot splash + `bg_color`, soft shadows, physics interpolation, input by `physical_keycode` (not logical keycode) with gamepad mapping when possible.

## Architecture by scale (do not over-engineer)

Pick the tier that matches the game. Over-architecting a small game is as bad as under-architecting a big one.

- **Small / medium (most jobs): a manager/director at the root of the game scene**, plus actors with an enum FSM (`enum State { IDLE, CHASE, ATTACK, DEAD }` + `match _state`), communication by signals, discovery by groups (`get_first_node_in_group`). No global event bus, no gameplay autoloads (the only autoload is usually the MCP helper).
- **Durable state across scenes (runs, economy, progression): one run-state autoload** (lives, coins, upgrades) exposing computed multipliers, plus a central scene orchestrator with a single damage entry point that locks state immediately so simultaneous hits do not compound.
- **Large, cinematic (orchestrated horror): service autoloads + an `Events` bus + a director.** Rule: "gameplay objects emit, UI and directors listen, no hard scene references." A Director node centralizes pacing in layers (scripted at milestones + ambient by thresholds + random in the silences).

**Common to all scales:** Rule 1c's separate saved scenes for every element, focused scripts, and an orchestrator that coordinates rather than constructing the game. Use data-driven content with custom `Resource` (`@tool class_name EnemyData extends Resource`, one base scene/script + N `.tres` = N archetypes), inheritance for variants (base scripts with virtual hooks, inherited scenes that only override the reward), mirrored `scenes/` and `scripts/` organization by domain, named containers per type, and production-quality code (static typing, `##` docstrings per system, defensive access, `&"StringName"` for signals/groups/actions).

## When you are handed a game proposal or "make X game"

Default assumption: the user wants a **product-ready, steam-ready, polished** result, not a prototype. Work in this order, MCP-first throughout:

0. ⛔ **Fix the scope first (quick gameplay):** read `references/quick-gameplay/quick-gameplay.md` and check the GDD's opening quick gameplay block (one signature mechanic, three to five levels, each with what it shows). If the GDD has no such block at the top, add it there before building. If the GDD asks for much more, build the budgeted core first and polish it to the bar before any extra content, and say so in the report.
1. **Confirm the Godot MCP is connected** (`fennara_status` / `editor_state`). If not, ask the user to open Godot and connect the plugin.
2. **Set the project stack:** Forward+ + Jolt + D3D12 + TAA, via `project_settings`.
2b. ⛔ **Install the boot mute RIGHT NOW, before any gameplay code, scene or sound exists** (Marco, 2026-10-05: *"as soon as it starts, mute it, and then carry on with the rest by yourself"*). Create the `Audio` autoload that mutes the Master bus in `_ready()` and the `toggle_mute` (`M`) action, then run the game once and confirm the bus is muted. Every test run, screenshot run and MCP `project_run` for the rest of the build is then silent, because Marco is at the PC while the agent works and an unmuted build makes noise on every launch (sound effects, music, 300 noises). Never leave the mute for the end or for the audio step. The speaker + `M` indicator can come later with the HUD, but the muting itself is step 2b, no exceptions.
3. **Map the elements to separate source scenes, then greybox the core loop** with primitives through the MCP. Build the element scenes first, compose instances in the level, and attach focused behavior scripts. Get the mechanic playable without a node-tree constructor.
4. **Tune the `WorldEnvironment`** early (tonemap, glow, SSAO, fog, grade). Screenshot to confirm. This is the biggest perception jump. **If there is a concept image, run the concept match loop here and after every later visual step** (Rule 2, concept match): comparison saved, biggest mismatch fixed, repeat.
5. **Layer the juice:** tweens everywhere, multi-channel impact feedback, screen shaders, audio-visual sync by signal.
6. **Close the loop with themed UI:** intro, HUD, game over, win, all faded and pause-safe.
7. **Add audio:** never ship without audio, pool the one-shots. The Master bus is already muted since step 2b (never touch that to hear your own sounds; verify audio through code and the bus levels, not by ear). Add the speaker + `M` indicator here if the HUD does not have it yet (see Audio rule).
8. **Run the steam-ready checklist below.** Validate (`script_diagnostics` + `validate_scene`, zero runtime errors) and screenshot before declaring it done.

## Steam-ready checklist (verify before declaring done)

If something is not checked, it is not done.

- **Quick gameplay scope:** one signature mechanic (on screen under 10 s after Play) and at most two supporting ones; three to five short, visually distinct levels (eight at most without Marco's OK); full content cleared in about 2 to 5 minutes; nothing unpolished added to pad the count. See `references/quick-gameplay/`.

- **Zero z-fighting:** floors, tile seams, overlays, borders and world-space labels remain stable in motion at all supported zooms/angles and relevant states. No duplicate/coplanar visible faces; reopened scenes and clip/frame evidence inspected, with offsets and camera clip values recorded. See `references/z-fighting/`.
- **Concept match:** when a concept image exists, `docs/evidence/comparison-final.png` shows it next to the concept camera screenshot and they read as the same game (camera, horizon, light, palette); the numbered rounds are there too.
- **Render:** Forward+ + Jolt + D3D12 + TAA (Mobile renderer instead when the target device is a low end phone, and say so in the GDD); `WorldEnvironment` with filmic tonemap; selective glow + SSAO + fog; tinted ambient + deliberate grade; real PBR materials; mood screen shader and/or damage vignette; verified by screenshot.
- **Juice:** nothing snaps (tween + easing); spawn pop, fade-out instead of `queue_free`, `1-exp(-k*delta)` smoothing; layered impact feedback (flash + particles + vignette + shake + hit-stop); audio-visual synced by signal; single intensity curve when the mood calls for it; rejected feedback + legible damage cause. Juice measured at the perceptual gate (pixels/amplitude/alpha/count), not assumed from node existence; shake clears a perceptual minimum. Sprite hand-overs and transitions checked on a frame contact sheet (no one frame giant sprite, no visible swap).
- **UI / loop:** ⛔ **a real font downloaded from the internet, committed with its licence in `assets/fonts/`, and ZERO controls left on Godot's default or on no font at all** (walk the scenes to verify, including debug labels); zero default Godot controls (themed + animated); fades + complete screen states; pause-safe; closed loop with explicit FSM and clean restart. Placeholder audit passed (no world-space blockout, no floating gate labels, theme overrides audited); world-space bars are siblings that do not inherit flip; tests consume semantic getters, not node paths.
- **Expand / full-frame visual QA:** `display/window/stretch/aspect="expand"` in the final project and requested exports, desktop and mobile. Runtime captures at the design size, a smaller window, a wider aspect and a taller supported aspect confirm readable UI, usable controls and correct camera/world coverage. Menus, HUD, dialogs, pause, results and active gameplay pass without clipping, overlap, distortion, unintended black bars or uncovered scenery. Evidence and dimensions saved; see the opening acceptance rule and `references/launch-settings/`.
- **Audio:** the audio mode is declared. Default ships SFX and/or music (do not ship a game without audio) with pooled one-shots, loops set, reactive audio where it applies. **The Master bus boots muted and `M` toggles it, installed at the START of the build (step 2b), not at the end** (works while paused, on every screen, with a visible speaker + `M` indicator, nothing persisted, verified at boot). A zero-audio-footprint request means zero assets, zero players, zero playback, zero autoloads, and audio settings/UI removed, editor tooling kept.
- **Cameras and animation:** every camera is perspective (no `PROJECTION_ORTHOGONAL` anywhere, top down views are a high perspective camera); every 3D animation transition blends (~0.75 s default, 0.20 to 0.30 in for contact clips), blend times exported in the inspector; Tripo characters idle on `look_around`.
- **Assets:** sponsor assets untouched from download (`.import` defaults, no texture cap, no decimation); one folder per model; nothing placed only because a pack contains it. 2D generated sprites: one density at k = 1, zero rescaled files, view audit and frame checks done, credits closed against the balance (`references/sprite-generation-2d/` §13).
- **Main scene visible:** the root scene is `scenes/main.tscn` and its editor viewport shows the full game world before Play (Rule 1c), checked with an editor screenshot after a forced reload.
- **Architecture / code:** each game element has its own saved source scene and focused behavior; the level composes instances and the director only coordinates. Before Play, Marco can open each source scene, select its nodes, change dimensions or transforms, save and reopen with the edit preserved at runtime. No code-built node trees, no `@tool` scene builders, no monolithic game script, no fixed startup overrides of authored dimensions. Signals/groups or event bus by scale; data-driven Resources + inheritance for variants; static typing, docstrings, public APIs, defensive access.
- **Build hygiene:** no hardcoded DEBUG flags; MCP/agent tooling removed from the final build; input by `physical_keycode`; `script_diagnostics` + `validate_scene` green, no runtime errors.
- **Playtest, not only the suite:** on anything Marco will look at, the last pass is a LOOK, not a green check suite. Boot it, put the camera where a player's is, screenshot, read the frame including the HUD text, and ask him to play it before calling it done. The checks you write encode what you already believe; a playtest is the only pass where the thing gets to disagree with you (RIFTFALL, 2026-08-09: eleven validators, a passing build and a headless end to end run of the boss fight were all green while the mission was playing the campaign's ending content, printing the wrong level number in the HUD and spawning a level 21 roster in mission 2; every one of those was found by Marco playing it and sending a screenshot). When he sends a frame back, treat it as the highest value signal in the session and pull the thread: the HUD reading "L21." was a cosmetic typo on the surface and a campaign finale bug underneath.

### Third person camera without lag or jitter

`references/third-person-camera/` (doc + `player_camera.gd`). "Camera lag" showed up THREE times in Paintfall, each time from a different cause. The counterintuitive part, and the mistake you will make by default:

1. **Position follow is RIGID, no lerp, on all three axes.** The classic `position.lerp(target, 1-exp(-k*dt))` has steady state error: with `k=12` the camera sits 0.50 m behind while running at 6 m/s and 2.0 m behind while falling at terminal velocity. THAT is the lag you feel, and no reasonable `k` fixes it. Fortnite, Mario and Zelda are rigid in position.
2. **Smoothness goes in rotation, FOV, spring length, shake and punch**, never in the follow position. There it does not displace the framing relative to the body.
3. **Against jitter you need all three things together:** `physics_interpolation = true` with `physics_jitter_fix = 0`, the camera reading `get_global_transform_interpolated()`, and `reset_physics_interpolation()` after EVERY teleport (player, projectile pools, respawning platforms).
4. **The rig carries an intermediate `ArmEnd`:** `SpringArm3D` positions all its direct children, so a shoulder offset set on a `Camera3D` child of the spring gets overwritten. `top_level` pivot → SpringArm → ArmEnd → Camera.
5. **Verify with numbers, not by eye:** debug label with `trail_xz` (must be 0.000 at top speed) and `trail_y` (constant, = `follow_height`, while falling). Any value that grows with speed is a hidden lerp.

### Third person player controller (facing + free look)

`references/player-controller/` (doc + `player.gd`, `player_camera.gd`). Reaching the shooter standard (W shows the back, S the front, A/D the profile) seems trivial and cost three non obvious bugs:

1. **The model faces the INPUT, not the velocity.** Velocity chases the stick through the whole acceleration ramp, so a model that faces the velocity runs crooked at every change of direction. Velocity is only a fallback when there is no input (knockback, ice).
2. **The model's yaw lives in its own variable and is written as a full triple euler, never read back from the node.** The classic `model.rotation.y = lerp_angle(model.rotation.y, ...)` is a read-modify-write on the basis, and since Godot's euler decomposition changes representation per quadrant, the loop settles offset (in Paintfall: exactly 90°). Same rule for the camera's yaw and pitch.
3. **The CharacterBody3D NEVER rotates** (`rotation = Vector3.ZERO` always). Facing is computed in world space but applied in local space, so a rotated body (typical: copying the SpawnPoint's whole `Transform3D`) injects a constant error into the WHOLE game. Take the position from the spawn; its basis only feeds the initial yaw of the model and the camera.
4. **Mouse: a single sensitivity in °/px for both axes** (`0.1375 °/px` at 1.0 is the industry standard). The classic trap is an extra multiplier on pitch that leaves the vertical axis stuck.
5. **The yaw offset when aiming is MEASURED, not tuned by eye:** it is the spine twist of the aim pose, obtained by FK from the clip. If the character or the pose changes, it is measured again.
6. **Verify with numbers AND WITH THE CAMERA ROTATED:** delta between the skeleton's real yaw (leg vector) and the commanded one must be ~0°. Bug 3 only showed up with the camera rotated, never from the spawn.

### Main menu with camera cuts over the live world

`references/menu-camera-cuts/` (doc + `menu_camera_director.gd`, `menu_camera_shot.gd`). The menu loads the SAME scene as the game with the UI on top, and a director camera tours the level in shots that **hard cut**, like a looping trailer. Two small scripts, zero timelines.

- **Tree order IS the edit:** each shot is a `Node3D` whose own transform is the initial framing; reordering nodes reorders the sequence and `enabled = false` removes a shot without deleting it.
- **Hard cut between shots, smooth movement within.** No blend or fade: the next shot is sampled at `t=0` and the camera teleports. If a cut feels bad, the problem is the edit (two similar shots), not the blending.
- **Nothing stays still:** inside each shot there is always a dolly or orbit, and the world behind has to be ALIVE (platforms dripping, NPCs patrolling). A frozen world kills the effect.
- **Preview it in the editor** with `preview_shot` + a `preview_t` slider, without running the game.

### Platform enemies that do not jump into the void (edge guard)

`references/enemy-edge-guard/` (doc + `paint_slime.gd`). A naive chaser (`dir = player.pos - self.pos`) suicides at the first gap and the level runs out of enemies: the game loop dies. A single raycast fixes it, with no navmesh.

- **Check the LANDING point, not "ahead of me".** The classic downward ray at a fixed distance fails with jumping enemies, because the jump covers a discrete distance. `land` is derived from the **real movement formula** (jump: horizontal velocity × flight time `2·vy/g`). If the enemy's `vy` or gravity changes and it is not recalculated, the guard lies.
- **Ray from `land+0.6` to `land−3.0`, mask world layers only.** The margin above tolerates edges with a lip; the 3 m below accepts a small intentional drop but rejects the void. Other enemies and the player do NOT count as floor.
- **When blocked, a short cooldown goes in** (0.35 s) and it re-checks, instead of spamming the ray every frame. The enemy stays threatening at the edge and resumes the chase instantly.
- ⚠️ **The test has to be DIFFERENTIAL:** "did not move" also passes if the enemy is asleep or bugged. The same enemy is tested with a gap (drift ≈ 0) and with continuous floor (drift > threshold). The negative case alone gives a false PASS.

### Satisfying 3D paint splash (Splatwalk)

`references/paint-splash/` (doc + shaders, scripts, scenes, materials, six generated splats and reference captures). What Marco marks as beautiful: **the paint puddle (the decal) and all the juice around it**. ⛔ **In every game where paint is thrown, sprayed or splashed, this module is mandatory** (Marco, 2026-10-17: *"that is key for anything 3D paint because it feels GOD"*). The feeling comes from stacking six layers ON the impact frame, not from a sphere with a texture:

- **Ball** at 40 m/s with a swept ray every frame and a trail; pooled **burst** of 16 droplets (0.55 s, curve that shrinks them to zero) oriented to the normal; a wasted shot is the same burst at 0.3.
- **Pop in** of 0.22 s with back ease: measured peak 1.15, never linear or instant.
- **Stain** as a wet slab with a shader (clearcoat, 0.22 self illumination so the paint never reads dark) on floors and bridges, and as a **`Decal`** that wraps the surface on walls and puddles, with six shapes, emission 1.2 and matte ORM so the color is the same in sun and in shadow. **Characters go on their own visual layer and the decal ignores them.**
- **Drips** hanging off the edge along the world down direction, cut by a ray; splatter if the stain rests on a surface; wet **sound** with random pitch.
- **The ball lands where the crosshair aims**: it passes through surfaces more than 0.9 m from the crosshair point (measured 0.01 m of error against 3 to 4 m before).
- ⚠️ **`Decal` does not exist in the Compatibility renderer.** Check the renderer first (relevant on Xogot and mobile); the doc includes the fallback with a quad.

### Satisfying tycoon: back stack, stations and physical money (fishing first)

`references/tycoon-juice/` (doc + 12 scripts verified headless on Godot 4.7.2 + 3 tests). Marco's request, 2026-10-17: *"everything from the fishing one: the wild stacking on the back stuff, cut fish... EVERYTHING that makes a tycoon satisfying has to be complete, so with this skill we can make more tycoon style games."* ⛔ **In every game whose loop is gather, carry, process, sell, spend and unlock, this module is mandatory.** The thesis: **every value is a physical object that travels and every arrival is acknowledged.** A tycoon without that passes the functional tests and reads like a spreadsheet.

- **Five layers on every arrival:** arc flight with stretch, squash on landing with back ease, ripple on whatever receives it, sound with a pitch ladder (+5 to 6 % per step, cap 2.0) and a floating number with a rolling counter.

Measured at 5 m/s: the base lags 0.09 m and the tip 0.39 m. Sway that grows with height, 4 degree wobble, 0.3 s arc pickup with slot reservation, upward ripple, "MAX" over the head when full and a reject cue.

### Ambience props with real collision

`references/level-props/` (doc). A bare level feels like a test map, but visual only props get walked through and break the illusion at the first brush.

- **Visual and collision SEPARATE:** the prop is a normal instance with whatever transform you want, and the collision is a sibling `StaticBody3D` with a primitive shape **shared per family** (4 to 6 primitives cover a whole game). Putting colliders inside the imported GLB scene is fragile: the import gets regenerated.
- **The body goes at the base of the prop** and the child `CollisionShape3D` is offset `height/2` upward, so the same shape works on any platform without recalculating centers. Collision layer = the world's, which also makes the enemies' edge guard count them as floor.
- **The collider is always a bit smaller than the visual.** Brushing past feels good; hitting invisible air is awful. Distant or fallen decoration gets no collider (they are invisible trip hazards).
- **Composition:** group in clusters at the edges, never sprinkle equidistant; vary rotation and scale on every instance; and **never a prop on the jump line**.
- **Verify by walking AGAINST the prop and reading the velocity**, which must drop to 0.00 with sustained input. The screenshot is no use: the third person camera hides small interpenetrations.

> ⚠️ That doc has a section of traps when editing `.tscn` by hand. **That does not apply here: Rule 1 (MCP-first) rules and scenes are created and edited through the MCP.** The section is only useful to understand why a scene reverted by itself if it ever happened.

### Props on bones (GearMount)

`references/gear-mount/` (doc + `gear_mount.gd`, `weapon_mount_profile.gd`, `muzzle_tip.gd`). The three points that cost dearly if ignored:
1. **Meshy and Mixamo rigs come at 0.01 scale** (centimeters). The prop inherits that scale, so the mount compensates by reading the scale of the **Skeleton3D**, never the basis of the `BoneAttachment3D` itself (that basis is garbage until it resolves the bone bind, and reading it earlier bakes broken transforms into the scene).
2. **Calibration lives in a `.tres` (`WeaponMountProfile`), not in the scene.** The profile rules and overrides the prop's transform on every load. Flow: viewport gizmo → tick `Capture From Gear` → save. Moving the prop without capturing is lost.
3. **`_write_profile()` requires `is_node_ready()` and `Engine.is_editor_hint()`.** Without those guards, the exported setters that fire one by one on load write the profile half done, and a game run can break the calibration. Do not remove those guards.

The mount uses `use_external_skeleton` to live under the Player and not under the skeleton: that way it survives swapping the whole model for another with the same rig.

### Combat: why the enemy "takes no damage" (vulnerability)

`references/combat-vulnerability/` (doc + `combat_hitbox.gd`, `combat_hurtbox.gd`). Starling's boss took no damage because of two bugs that combine, and both are easy to repeat:

1. **Physical state is not a bool.** Changing `hurtbox.enabled` does not change `monitorable` or the shape: the enemy looks vulnerable in code and not in physics. The fix is a single `set_enabled()` API that touches the bool, `monitorable` and `CollisionShape2D.disabled`, all with `set_deferred` (physics changes inside a signal callback go deferred).
2. **Deduplicate ACCEPTED hits, not attempts.** If the hitbox registers the receiver BEFORE knowing whether the hit was accepted, an overlap during invulnerability consumes the swing and, when the vulnerable window opens, the same attack no longer retries. The hitbox adds the receiver to its dedup only if `receive_damage()` returned true.
3. **`area_entered` is not enough on a persistent overlap.** The signal fires only once, when contact begins. If the swing was already inside when VULNERABLE opens, no new event arrives. The active hitbox re-queries `get_overlapping_areas()` every physics frame (only with `active` and `monitoring` true) through the same damage path.

The vulnerable window exists physically only during VULNERABLE, with a tint to read it, and it is tested with the player's REAL attack (including the persistent overlap), never with damage by direct call. An accepted hit gives flash + knockback.

### Screen fades and transitions with ownership

`references/screen-fade-transition/` (doc + `screen_transition.gd`). An instant scene change or respawn reads as a prototype. A global fade needs more than a tween:

- **A global `CanvasLayer` with `process_mode = ALWAYS`** (keeps running while paused), a **cancellation serial** that kills the previous tween so two requests do not fight, **observable phases** (hold, fade_out, scene_change, fade_in, idle) that tests and callers can read, **mouse blocking while black**, **rollback on error** (if `change_scene_to_file()` fails, fade in and emit an error), and **cleanup in `_exit_tree()`** so a scene destroyed mid transition does not leave the game stuck.
- **A single owner:** the world coordinates the respawn through the same global layer, not each system with its own fade.
- ⚠️ Trap: the `ColorRect` keeps base alpha 1 and the tween animates `modulate.a`; animating modulate over a base color with alpha 0 leaves the overlay invisible. And tests wait for an observable condition with a timeout (`not visible and not transitioning`, idle phase), never a fixed number of frames.
- **A slow transition is almost always loading, not animation** (measured in Reedway Ferry, 2026-09-24): each scene preloads its next likely scene in a thread at startup (`ResourceLoader.load_threaded_request`, with the `PackedScene` referenced) and the travel went from ~1.3 s to 0.65 s. ⛔ **Between places in the world, the transition scales toward the destination and then changes** (Marco): camera dive, capture of the last frame on top, new scene underneath, crossfade of the capture and arrival zoom with ease. Script: `scripts/travel_fade.gd`.

And `reset_physics_interpolation()` after showing or teleporting, or a giant frame appears.

### 2D water with wake (a single surface)

`references/water-foam-2d/` (doc + Reedway Ferry shaders and scripts). ⛔ **Water and foam are ONE surface, never two layers** (Marco): the water is a world space shader with an animated cell network; the boat only paints a mask into a `SubViewport` that copies the camera, and the water turns it into foam with its own cells. The foam goes from white to transparent with age, stern wake only. The wake is a triangle strip with the exact age in UV.x (a `Line2D` makes the foam jump), the mask mixes normal with density in RGB and coverage in alpha (additive makes streaks, `blend_disabled` makes holes), it is cleared on every teleport, and the shared material is duplicated in the scene that binds the mask.

### 2D UI: from placeholder to visual system

`references/ui-polish-2d/` (doc). How to turn floating Labels and blockout `ColorRect`s into a real HUD, dialogue and prompts:

- **Palette and tokens in one place, but audit the overrides:** a Theme is not enough, colors escape through `theme_override_colors`, `modulate`, `self_modulate` and scripts. Centralize the palette and sweep those four sources in scenes, resources and code.
- **World space bars = siblings of the `AnimatedSprite2D`, never children**, so `flip_h` does not mirror the UI. Verify the position against the large clips (attack, air_dash), which invade the bar's space even if idle looks fine.
- **Nested UI belongs to its owning scene:** the interaction prompt lives in `npc_interaction.tscn`; editing it from the NPC's scene does not serialize. Inspect ownership before touching a visible node.
- **UI density against the viewport, not minimized:** shrinking is not the default. In Starling the final sweep went UP (larger HUD and dialogue, bigger typefaces), because shrinking the dialogue left it illegible and with dead space. Calibrate size with two screenshots (isolated UI + UI over the densest area) comparing legibility, space and occlusion. It goes with the preference for large, legible UI: when in doubt, bigger.
- **Dialogue with a two action typewriter + semantic tests:** the typewriter reveals at N chars/sec (accumulated as a float to be framerate stable) and the input separates TWO actions, the first completes the line, the second advances, so pressing fast does not skip content. Expose getters (`get_core_count()`, `is_transitioning()`, `is_typewriting()`, `get_visual_alpha()`) so probes do not couple to internal paths.

### Mobile UI, touch and guided tutorial

`references/mobile-ui-touch/` (doc). Contracts measured in Idle Acres on a real Xiaomi:

- **Design and review at the phone's real aspect from day one.** The desktop preview uses that aspect, not a generic 16:9. Each HUD is anchored to its edge and every visual change is validated with a runtime screenshot.
- **Legible text without clipping:** the copy stays inside the interior area of the frame using best fit with an explicit minimum. Icon and value are measured as a single group. Shrinking the whole system is not the default answer.
- **Catalog without gaps or duplicates:** unlocked first, one locked preview per id, and every null, duplicate or omitted card is hidden before the sort and the reflow. An omitted card carries a semantic flag such as `show_in_catalog`, not a transparent plate that occupies a slot.
- **Direct touch:** long press enters move without opening the Move/Sell panel; successful placement keeps the item armed to repeat and charge; closing, canceling or switching items disarms it. Every grass tile that reads as buildable accepts placement.
- **Tutorial by semantic events:** advisor, acknowledge, exit, overlay, spotlight and hand. The hand takes no input and aligns by the fingertip with a local offset. Close overlays before asking for spatial gestures.
- **Anchor animated art by the feet:** advisor, animals and characters have scale and offset per clip or expression. Floor contact does not change when the state changes.
- **2D seams in fractional preview:** if the design canvas is reduced to a desktop window with a non integer scale, use `viewport` plus snapping of transforms and vertices. Pixel snap alone does not fix the subpixel row created by `canvas_items`.
- **Verifiable Android delivery:** exporting is not enough. Install, launch, confirm PID and resumed activity, read the crash buffer and look at a real capture.
- **Vehicle game (Reedway Ferry, 2026-09-24):** ⛔ FIXED joystick (center on PC, left on phone), the push distance is the throttle; one second interaction inside the ring at any speed; minimal HUD; title with a simultaneous crossfade showcase; buildings that start black, a linear unlock order and one visible bonus per building; coins flying above all the UI.

### Concept match (concept vs gameplay, camera, light and environment)

`references/concept-match/` (doc + `compose_comparison.py`). It was born in Emberpine Cabin (Atlas) and became a rule in Tide Runner (Pixelfork, 2026-09-13):

- **The concept is the acceptance test, not a mood board.** A `ConceptCam` camera (or a `ConceptPose` that the gameplay camera adopts at startup) lives in the saved scene, with a dev only snap on Tab.
- **The zone the concept shows is authored by hand**, never spawned: in a runner it is the first chunk, in a scene it is the whole scene.
- **Photo after every visual milestone**, at the design resolution, composed concept left / capture right with the script, saved numbered in `docs/evidence/` and never overwritten. The biggest mismatch is fixed first, in a fixed order (horizon, distance and FOV, subject position, silhouettes, props, background, sky, water, sun, fog, glow, grade, UI). Five to ten rounds.
- **Light is matched by values** (hex colors, sun elevation and azimuth, fog, tonemap, saturation, contrast) written in the GDD before and in `BUILD_NOTES.md` after.
- **And with a luminance table MEASURED on the concept** (mean in gray 0 to 255, percentage of pixels under 64, sample of the floor or the snow): without numbers the agent "matches" by eye and the build comes out dark (Marco, 2026-09-20: *"sometimes the whole scene comes out dark... it has to be bright"*). A frame out of range is a blocking bug and is fixed with exposure, ambient and sun before materials. When the brand already has an approved game, its `Environment.tres` is copied to the new project as a baseline (Steam and Snow starts from Hardhat Hollow's `hollow_environment.tres`). The Kenney CC0 skyboxes (`Skyboxes 1.0`: day, morning, night, space, alien) live in `Tripo\4-tripo\assets\skyboxes\kenney\` and are copied to `assets/skybox/`.
- **Do not judge from the MCP thumbnail:** open the composed PNG at real size before closing the round.

### Building with `xo` in Xogot (measured gotchas)

`references/xogot-xo/` (doc). It came out of the entire Container Yard build (Xogot for Mac video 2, 211 `xo` calls, 49 with errors) and Miguel de Icaza asked for it to improve Xogot's official skill (2026-09-27). **Read it before any build through `xo`**, together with the `xogot` skill that the repo carries. What costs the most if you do not know it: saving a scene to a folder that does not exist writes nothing (or leaves it in `res://`) and the response still shows the requested path; editing a script with exports resets the instances of open scenes and the next save stores the defaults; negative numbers are read as flags (`--position=-2,0,9`); `xo eval` only says `errParseError` (almost always `:=` on a Variant); `project run` opens a second instance and from then on everything carries `--app`, resolved by `xo list`; and `xo test run` does not test gameplay, behavior suites go through `xo game eval --file`.
